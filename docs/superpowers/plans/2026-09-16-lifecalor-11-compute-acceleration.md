# LifeCalor 1.1：算法加速、计算设置与有界大数据计算

- 日期：2026-09-16。
- 状态：研究与实施规划，尚未实现，也没有目标 GPU 的实测加速比。
- 代码基线：`278cafb`，当前应用版本 `1.0.16`。本次不修改算法、依赖、应用版本或更新日志。
- 研究范围：定向阅读 STFT、CWT、寿命拟合、关联预处理、任务协调和数组缓存；不是全仓库审计。
- 硬件假设：用户所述“intel 5070ti”暂按 **NVIDIA GeForce RTX 5070 Ti** 理解；桌面版和笔记本版分别考虑，实际型号由未来软件在目标电脑中识别。本次不查询开发电脑硬件。
- 最新用户约束：日常也使用 `float32`；此前提供的巨大尺寸与 `complex128` 是极端情况。**原有默认精度不变，精度作为算法设置中的独立选项。**
- 交付方式：后续实现者按阶段实施并记录证据；没有真实目标硬件时，不把 CUDA 验收或 TB 级实测标为完成。

## 1. 结论与边界

**值得加入可选 GPU 加速，但 1.1 的核心应是“统一计算策略 + 有界分块 + 可验证的 CPU/CUDA 后端”，不是把所有 NumPy 数组直接转成 GPU 数组。**

STFT、批量 FFT 和 CWT 是优先候选；寿命拟合需要独立评估。小 ROI、单条曲线和短任务往往不值得支付设备初始化与传输成本。算法能在 GPU 运行、结果合格、端到端更快，是三个不同的验收条件。

不扩大到以下事项：MainWindow 行数指标、全仓库清理、计算器全面 GPU 化、显示层重写、强制更换缓存格式、全平台 GPU 后端同时支持、所有历史线程同时并发。已验收的名称、标签、历史、导出、画布和主题行为保持不变。

### 1.1 显卡与精度判断

RTX 5070 Ti 桌面版标称 16 GB 显存，笔记本版标称 12 GB；不能按同一容量和持续性能估算。[NVIDIA 桌面规格](https://www.nvidia.com/en-us/geforce/graphics-cards/50-series/rtx-5070-family/)、[笔记本规格](https://www.nvidia.com/en-gb/geforce/laptops/50-series/)

RTX 5070 Ti 的 CUDA Compute Capability 为 12.0；官方架构表给出的 12.x 非 Tensor Core FP32:FP64 吞吐比例为 64:1。这意味着双精度不是该系列的强项，**不意味着某个 FFT 必然慢 64 倍，也不能推导相对 CPU 的速度**。[型号对应表](https://developer.nvidia.com/cuda/gpus)、[架构精度吞吐表](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html)

据此判断：日常单精度批量运算更值得优先验证；双精度和复数双精度仍可纳入后端，但 Auto 必须依据相同精度下的实际收益选择。游戏帧率、AI TOPS、DLSS 指标不作为科研计算加速依据。

### 1.2 数据规模

以下为单份输入，不含输出、临时数组、FFT 工作区、数据副本和操作系统缓存；GB/TB 使用十进制。

| THW | 元素数 | float32 | float64 / complex64 | complex128 |
| --- | ---: | ---: | ---: | ---: |
| 10000 × 400 × 400 | 1,600,000,000 | 6.4 GB | 12.8 GB | 25.6 GB |
| 100000 × 1024 × 1280 | 131,072,000,000 | 524.288 GB | 1.048576 TB | 2.097152 TB |

即使当前 12.8 GB 输入表面接近 16 GB 显存，也不能连同中间结果整组上传。未来尺寸必须支持输入和结果都不完整驻留内存/显存。

两个说明计算量的例子，不是固定输出承诺：

- 若 STFT 保持窗口 128、重叠 120、边界补齐的约定，未来 T=100000 的输出时间点约 12501；仅一个选频幅度 THW 输出，float32 就约 65.54 GB。实际尺寸必须由准确的边界规则计算。
- 未来尺寸若完整保存 256 个尺度的 complex128 CWT 系数，需要约 536.87 TB；因此必须分尺度计算并即时归约，不能先构造完整系数体。

极端尺度用于验证资源规划不会溢出、不会整组分配；首轮性能验收仍以实际常用数据为主。TB 数据还受磁盘有效吞吐制约：假设连续读速为 1 GB/s，仅读取 1.048576 TB 就约 17.5 分钟，这是算术示例，不是目标电脑测速结果。

## 3. 后端与精度分开设置

### 3.1 后端策略

全局默认后端为“自动”，每个算法可选择“跟随全局 / 自动 / CPU / GPU”。

| 选择 | 规则 |
| --- | --- |
| 自动 | 先检查算法、dtype、设备、资源和验证状态，再比较预计端到端耗时；无可信收益信息时优先 CPU，不试跑整组数据 |
| CPU | 强制 CPU，使用经验证的串行/批量/多核方案；不因存在 GPU 改变选择 |
| GPU | 优先所选 GPU；设置“不可用或资源不足时允许 CPU 回退”，默认勾选；关闭即严格 GPU，不能悄悄切 CPU |

任务界面明确显示请求后端和实际后端，以及“数据较小”“该模型暂不支持 GPU”“双精度预计无优势”等选择原因。切换设置只影响尚未提交的任务；排队任务已保存自己的参数快照，不被后来设置改变。

首发生产后端是 NumPy/SciPy/PyWavelets CPU 与 CuPy/CUDA。Intel、AMD 显卡仍应能展示基础型号；标注“本版本未适配计算后端”，不是“硬件不支持计算”。不在首版同时维护 SYCL、OpenCL、ROCm、DirectML 等多套数值实现。

### 3.2 精度策略：默认兼容原有行为

**“后端自动”绝不等于“精度自动降低”。** 精度在任务计划形成时固定，减小批量、重试或 CPU 回退均不得改变它。

| 精度选项 | 明确定义 |
| --- | --- |
| 兼容现有（默认） | 按算法冻结的现有有效路径，保留输入转换、主要中间精度和输出 dtype；允许原来就是单精度，不把全部算法升级为 float64 |
| 保留输入精度 | 对浮点/复数输入，不主动降低有效精度；按算法允许更高精度的归约或拟合。实数 FFT 产生对应复数，复数幅值产生对应实数 |
| 单精度 | 显式选择 float32 / complex64 计算策略；只有通过误差验收的算法才开放，不保证比双精度结果完全一致 |
| 双精度 | 显式选择 float64 / complex128；增加内存与显存需求。由低精度原始数据升精度不会恢复已丢失的信息 |

实施要求：

- 用算法精度描述表定义 `input_cast / compute_dtype / accumulator_dtype / output_dtype`，而不是全局一次 `astype`。界面显示解析后的“输入 → 计算 → 输出”，复杂混合精度放 tooltip。
- 兼容模式首先从 CPU 代码建立样例和 dtype 契约。FFT 中 NumPy 与 CuPy 的 dtype 推导不能假设一致，显式处理并验证。[CuPy FFT 类型说明](https://docs.cupy.dev/en/stable/reference/fft.html)
- 寿命拟合等现有双精度求解器，不因用户点“单精度”就只把输出转 float32 冒充计算加速；未适配的组合禁用并说明原因。
- 整数输入按算法原有规则转换；新增保留模式按数值范围制定浮点转换，检查溢出与有效位，不把 uint16 减法留在无符号类型中。
- 复数策略保留实部与虚部。既有只对实数定义的预处理/寿命算法遇到复数，应拒绝并说明需要明确观测量；不得通过转 float32 静默丢虚部。abs、功率、real 是不同科学含义，不能自动任选。
- 不默认启用 FP16、TF32、fast-math，也不调整 nfft、尺度数、降采样或拟合容差来腾出显存。
- 结果 metadata 记录所选策略和实际各阶段 dtype；不回写、转存或修改输入原件，也不改变旧历史记录。

## 4. 统一计算架构

```text
现有算法对话框 / anchor / 其他计算入口
        |
不可变 ComputeRequest（数据引用、轴、参数、后端、精度）
        |
已有 TaskCoordinator + 资源规划 / 后端选择
        |
块读取 -> CPU 或独立 CUDA worker -> 块结果写入
        |
结果文件完成提交 -> ArrayRef + metadata -> ProcessedData
        |
现有 processed_result 路由、画布、绘图、历史、导出
```

### 4.1 模块组织

新增内容归入 `core/compute/`；仅在真正需要时拆文件，不制造空接口层：

| 模块 | 职责 |
| --- | --- |
| `model.py` | 请求、设备能力、精度描述、执行计划、块与结果描述；不依赖 Qt 或导入 CuPy |
| `capabilities.py` / `settings.py` | 异步探测入口、缓存能力结果、QSettings 迁移与校验 |
| `planner.py` | 精度解析、CPU/GPU 选择、块规划、内存/显存/磁盘预算与失败原因 |
| `executor.py` / `worker.py` | 对接现有任务协调器、spawn 工作进程、IPC、取消、心跳、重试 |
| `io.py` | 复用 ArrayRef、NPY 原子写入和已有内存工具，提供只读块与可提交输出；不复制一套缓存管理 |
| `backends/cpu.py` / `backends/cuda.py` | 各自调用已验证的数值库；CUDA 依赖只在 GPU worker 内延迟导入 |
| `algorithms/` | 按 STFT、CWT、寿命等划分数学约定、块边界与后端调用；不把所有算法搬入巨型通用函数 |
| `dialog.py` | 统一计算设置、硬件表和共享算法选项控件；遵循现有 Qt 主题、字体和工具栏风格 |

`DataProcessor`、`LifetimeCalculator` 保留当前公开入口作为适配层；`MainWindow` 只增加必要信号与设置入口。已有 CPU 入口在迁移验收前不能一起删除；新旧分支通过定向回归后再去除重复内核。

### 4.2 数据契约

- 请求携带稳定数据 ID、版本、ArrayRef 或受控的内存块句柄、shape、dtype、实际轴语义、time_point、fps、单位、ROI 和算法参数；不能为构造请求触发整组缓存恢复。
- 使用 THW，且不能把所有三维矩阵都当视频。非 T 轴的体数据只进入支持它的算法，THWC 彩色数据先通过明确的通道规则，不自动展平成像素时间序列。
- 任务期间输入只读并获得引用租约。用户仍可选择其他历史、查看其他画布；删除/清缓存不能移除正在使用的文件，释放任务租约后才回收。
- GPU ndarray 不进入 Data、ProcessedData、out_processed、历史 JSON 或 Qt 图像对象。进程只回传进度、诊断、小 metadata、共享块描述或已提交文件引用。
- 大输出直接成为现有 ArrayRef，避免先拼成 ndarray 再调用缓存机制二次落盘。小输出保留现有内存路径。512 MB 等用户缓存阈值不等于显存块预算；有界计算需要流式输出时可直接临时落盘。
- metadata 保留父数据关联、有效单位、帧/频率/时间轴以及结果类型；大 `out_processed` 也走结果写入器，不能借参数继承深拷贝输入大数组。
- 新增 `compute` provenance 字段：算法版本、请求/实际后端、精度策略、实际 dtype、参数、设备摘要、库版本、分块规则、回退原因、各阶段耗时。不记录原始数据内容或不必要的设备序列号。

## 5. 分块、资源与磁盘

### 5.1 有界资源计划

统一用 `math.prod(shape) * np.dtype(dtype).itemsize` 和 Python 整数计算字节数；偏移用足够宽的整数。当前未来尺寸已经超过 32 位元素计数；不能把原始字节计数直接发送进 `pyqtSignal(int, int)` 或 QProgressBar，任务记录保留完整计数，UI 映射到固定进度范围。

规划分别核算：主机活跃块、固定内存传输缓冲、设备输入、输出、FFT/CWT 工作区、归约临时量、库内存池、计划缓存、并发队列和磁盘临时文件。对第三方 FFT 的批次/索引限制也做校验，不能因为 Python 能表示大 shape 就传入超限单次变换。

建议初始安全默认值，须目标机验证后锁定：

- 显存使用上限默认总量的 70%，同时扣除当下其他占用并保留至少 `max(1 GiB, 总量的 10%)` 空闲余量；以每次分配前的实际状态复核，不把上限当作已经预留成功。
- 主机 RAM 预算复用并扩展现有内存设置，计入所有活跃任务和缓冲，不按输入大小直接扩大。
- pinned memory 只做有界传输缓冲，初始上限 `min(256 MiB, 主机任务预算的 10%)`；双缓冲、预取加入后必须计入同一总额。
- 6/8/12/16 GB 等容量通过更小块适配；即使最小合法块也放不下时明确转 CPU 或拒绝执行，不强行分配。
- FFT plan cache 设置容量/字节上限。显存检查要区分池内已使用、池内可复用、驱动空闲，避免重复计数。[CuPy FFT 工作区与缓存](https://docs.cupy.dev/en/stable/user_guide/fft.html)

### 5.2 读取布局

THW 文件按帧连续，而单像素沿 T 是跨步访问。`reshape(...).T` 本身便宜，不代表之后的磁盘读取便宜；本轮不永久恢复完整 `unfolded_data` 副本。

STFT/CWT 优先采用时间段与空间块的联合规划，先连续读取适当的帧/行带，再在有界缓冲中整理为批量时间序列。需要记录读取放大率与重复读取次数，避免“内存省了，磁盘重复扫了几百遍”。

寿命拟合需重复访问完整时间曲线，按空间块收集一批曲线后在 RAM/VRAM 中完成该批拟合。必要时提供任务临时的像素主序中转文件，但须先估算额外整组读写与磁盘空间收益；不默认复制 TB 输入，不把它保存在历史参数里。

### 5.3 输出提交与回收

- 扩展 `core/dataio/npy.py`：允许先根据 shape/dtype 创建任务独有临时 NPY，然后 `write_block`，而不是必须先拿到完整结果 array。
- 继续使用 NPY/mmap + metadata；本轮不迁移已保存的数据为其他格式。更换存储格式只有在实测证明需要时另行讨论。
- 所有临时文件置于用户设置的缓存目录下、独立 task_id 子目录；启动前核算所有输出、临时中转和当前文件共存的峰值。磁盘不足不回退成全量 RAM。
- 写完并关闭映射后提交文件；多结果以最后的结果清单/完成标记作为唯一可见提交点，然后才注册 ProcessedData 与可恢复历史。取消、失败和进程崩溃不能留下可恢复的“半成品”。
- 1.1 首版不做崩溃后继续计算；清理仅限已确认无活跃租约的本任务临时产物，保留原始数据和已提交历史。CPU 回退需重跑阶段时删除该阶段未提交输出。
- Windows 文件映射的关闭、改名、引用计数、清缓存竞争必须测试；不删除别的任务或其他 LifeCalor 实例的同名共享资源。

## 6. 算法实施策略

### 6.1 STFT：首个主要 GPU 算法

使用 CuPy 的批量 FFT / `cupyx.scipy.signal.stft` 作为实现基础，避免自行编写 FFT。该接口具备窗口、overlap、nfft、boundary、padded、scaling 等选项，仍须逐项对齐本软件的定义。[CuPy STFT](https://docs.cupy.dev/en/stable/reference/generated/cupyx.scipy.signal.stft.html)

1. 先冻结 CPU 参考：同一窗口数组、时间轴、采样率、目标频带、幅度归约、单/双边和 dtype。处理 DC、Nyquist 与负频率，不能无条件将所有频点乘 2 后称为通用物理幅度。
2. 保留用户已测通的实数选频行为；发现需改变的归一化或复数负频率规则，作为明确的算法版本变更，不能藏在 CUDA 开关中。旧历史结果不重算。
3. 一个批次处理多个像素/窗口；仅在设备上保留当前块的频谱，选频、abs 和归约在设备内完成，回传最终幅度块。
4. 时间分块必须对齐全局 hop，内部边界只读取重叠 halo，不重新补零；首尾补齐只发生于原始信号边界，输出帧不重不漏，time_point 与整段参考一致。
5. CPU 也采用经验证的批量/线程化 FFT，避免把“修掉 Python 循环”的收益全部算作 GPU 收益。控制进程数与 FFT 内部线程数，避免过量嵌套并行。

### 6.2 CWT：先校准定义，再加速

PyWavelets 提供 conv/fft 方法；应先比较其 CPU FFT 路径。GPU 的同名 CWT 函数不等于 PyWavelets 的波形采样、积分核、尺度与截边定义，不能直接互换。[PyWavelets CWT](https://pywavelets.readthedocs.io/en/latest/ref/cwt.html)

1. 明确多尺度输出是否是 `mean(2 * abs(coeff_s) / sqrt(scale_s), axis=scale)` 等定义；在没有科学确认与样例前，不能仅为修 shape 自行选公式。当前单尺度结果作为兼容样例。
2. 首批仅开放经验证的实际使用小波；其余 wavelet 标注“CPU”，不通过悄悄换成另一小波来使用 GPU。
3. 使用匹配 PyWavelets 的离散核与 FFT 卷积，按时间、像素、尺度分批，按原有归约顺序/精度累计结果；绝不构造完整 S×T×P 系数体。
4. 根据最大有效核支持范围计算 halo；低频大尺度可能让 halo 主导内存与重复计算，应拒绝不合算的 GPU 计划或用 CPU，不改变用户频率范围。
5. 验证单/多尺度、实/复数、小 T、低频、不同 precision 与全局首尾及所有块接缝；库版本升级也要重跑此组对照。

### 6.3 寿命拟合：先消除确定浪费，再验证 GPU 求解

1. 统一单/双指数 CPU 参考的模型参数、边界、初值、峰后窗口、时间单位、噪声门限、失败掩码和 R²；修复第 2 节列出的调用/输出问题，不改变默认精度。
2. 通过已确认的规则完成噪声筛选后，每像素仅做必要次数拟合；滑动相关可批量计算，但常值、短序列、NaN 与阈值附近要和参考一致。
3. 先获得稳定的 CPU 分块/多核实现，避免全量共享内存副本。预卷积按空间 halo 处理，后卷积保持现有结果含义。
4. GPU 单指数拟合作为受验收约束的后端。先评估成熟的批量非线性拟合库，再决定是否需要专用内核；不是把 Python 的 curve_fit 放进 CUDA 线程就会运行。
5. 可评估 Gpufit：提供批量 CUDA 非线性拟合、约束及自定义模型入口，但其现成模型、精度、Python 绑定、现代 CUDA 构建和本项目时间轴/失败语义均需验证，不能当作直接替代品。[Gpufit 官方文档](https://gpufit.readthedocs.io/en/latest/)
6. 不以取对数线性回归替代带基线非线性拟合，不把不同求解器的更宽松停止条件当作提速。有效像素、寿命偏差、残差、失败率与边界命中都需比较。
7. 双指数先保证 CPU 正确可用；GPU 实验若未达到验收，明确保留 CPU，不为了版本号交付一个“可以勾选但未实现”的加速分支。

### 6.4 关联算法的范围

EM 预处理采用同一读写、精度与进度体系，CPU 分块是必做；GPU 仅在已驻留块可复用或端到端有收益时启用。背景 median、近零分母和全零背景必须有确定行为。

FFT2/IFFT2 可作为第一批 CUDA 正确性/资源自检，按帧批量执行；原始复数、幅值、相位等输出全部计入资源预算。一般复数逆变换不能自动取实部；仅在算法明确是实值重建时保留对应行为。

当前帧直方图、anchor 小 ROI 与单条质量分析默认 CPU。不要为了后端形式统一让所有轻量交互排在耗时 GPU 任务后面。

## 7. 任务隔离、取消与未来并发

- 复用现有 `TaskRegistry/TaskCoordinator` 的状态与任务 UI。扩展设备、精度、执行阶段和 attempt_id，不另建第二个任务列表或类别进度条。
- GPU 计算使用 Windows spawn 的独立进程，延迟初始化设备并可持续复用；进程不创建 Qt 窗口，不持有 Data 历史或 GUI 对象，不在每个 CPU 池进程中创建 CUDA 上下文。
- 首版一个选定 GPU 同时执行一个重型 GPU 任务，其余排队且可单独取消；协议从一开始带 task_id。CPU 是否可同时工作受全局 RAM/CPU 配额和已迁移入口限制，不承诺旧常驻 worker 立即支持任意并发。
- 新任务的所有参数、数据绑定与后端不可变。不得在任务运行时覆盖共享 worker 的 cancellation_token 或靠队列首项猜结果属于谁。
- 现有 CancellationToken 使用 threading.Event，不能把它直接当作跨进程取消令牌；通过 IPC/进程共享事件桥接。Esc 取消当前前台任务，任务列表可取消指定任务，不取消无关工作。
- 每块读取、传输、计算、写入及迭代边界检查取消。已提交的单次 GPU 内核未必能瞬时停止；界面显示“正在取消”，GUI 不阻塞 wait/join。
- 进度以已完成且确认的块/字节为依据，包含读取、传输、计算、写入和最终提交；GPU 异步提交不等于计算完成。初次编译显示明确阶段，耗时尚未知时不编造百分比。
- 启用独立心跳和超时诊断；常规取消超时后可由用户请求终止本任务的隔离计算进程，异步回收临时资源。取消不是错误，也不能触发 CPU 自动重跑。
- GPU OOM 可在相同精度和数学参数下缩小块，建议最多 3 次；仍失败且允许回退时，在清理当前阶段半成品后切 CPU 重跑该阶段，显示“重试”，保留进度记录，不伪造连续成功。
- 参数错误、结果不合法、数值异常、算法一致性失败不能用 CPU 回退吞掉；GPU 失效后的迟到结果按 attempt_id 丢弃，最终结果只能提交一次。
- 普通错误汇总成一个诊断事件，携带任务、阶段、shape、dtype、后端、块和资源预算；warning 不弹窗，info/warning/error 全部入日志，不逐行弹 traceback。

Windows 存在 GPU 超时恢复机制。优先短批次并实测 GUI 响应，不建议关闭 TDR 或修改系统超时注册表；独立进程能隔离部分计算故障，但不能保证驱动重置不会影响同卡 OpenGL 画布。[Microsoft TDR](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/timeout-detection-and-recovery)

### 8.2 默认策略与算法设置页

- 默认策略：自动/CPU/GPU、首选设备、允许 CPU 回退、CPU 并行配额、显存上限、主机工作内存上限；默认精度固定为“兼容现有”。
- 算法表：STFT、CWT、单指数寿命、双指数寿命、EM 预处理、FFT/IFFT；列出后端覆盖、精度策略、可用状态和设置按钮。
- 各算法原有参数对话框保留窗口、频率、小波、ROI、模型等科学参数；加入共享的紧凑“后端 + 精度 + 预计资源”区域，必要高级选项折叠。
- 批量默认自动规划；高级用户可限制块大小但不能跳过资源校验。tooltip 说明预算、精度损失和当前实际 dtype，不让用户猜“float32”仅指输出还是整个计算。
- 使用已有 QSettings，建议前缀 `compute/`。旧 CPU 加速/核数设置迁移为相应 CPU 偏好；已有用户的算法参数和默认精度不重置，未知旧键保持不动。
- 正在执行任务只在任务状态/现有右下状态入口显示后端和阶段，不恢复左下角逐帧闪烁提示。查看详细进度是用户操作，错误仍走统一诊断。

## 9. 依赖与适配策略

CuPy 是首选候选，因为与现有 NumPy/SciPy FFT 使用方式接近。维护 CPU 基础环境与可选 CUDA 依赖清单；不为硬件状态页面引入整套 PyTorch/JAX。

研究时 CuPy 稳定安装文档提供 Windows 的 CUDA 12.x/13.x 轮子及可选运行库组件，并对 Python/NumPy/SciPy 版本有要求。**不能直接升级项目全部科学依赖来追最新版**；实现阶段先读取项目虚拟环境版本，再选兼容、支持目标显卡的组合。[CuPy 安装要求](https://docs.cupy.dev/en/stable/install.html)

Compute Capability 12.0 不是 CUDA Toolkit 12.0。CUDA 12.8 发布记录加入 SM_120 编译支持；首批 Blackwell 构建应选择包含对应支持的运行库/NVRTC/FFT 组合，并在目标机器进行自检，不把所有 cuda12x 组合视为等价。[CUDA 12.8 发布说明](https://docs.nvidia.com/cuda/archive/12.8.0/cuda-toolkit-release-notes/index.html)

实施时锁定并记录 Python、NumPy、SciPy、PyWavelets、CuPy、CUDA 运行组件与已验证驱动范围。CPU 包无需 CUDA；GPU 包或可选组件的安装是显式操作。PyInstaller spawn、freeze_support、DLL 收集和未装后端环境都属于发布验证，不能只测开发环境 import 成功。

旧 NVIDIA 卡按所选运行库实际支持范围显示能力；不支持新 CUDA 包时仍可用 CPU，不向用户推荐不可用的 GPU 开关。多 GPU 先支持选择一个设备；同时跨卡计算和多厂商加速作为后续扩展，不列为 1.1.0 完成条件。

## 10. 验证与基准

### 10.1 科学一致性

- 构造小型确定性数据：整数、float32、float64、complex64、complex128；常量、零、脉冲、正弦、复指数、单/双指数衰减、噪声、NaN/Inf、短 T、非整除块长。
- 比较旧有效路径、统一 CPU 参考、新 CPU 分块、CUDA 分块；先验证 shape、轴、单位、频率/时间刻度、结果类型、有效/无效掩码，再比较数值。
- 兼容默认模式的 dtype 与旧有效路径一致。修正的 CPU 缺陷单独列出预期变化，不要求复现错误值，也不允许其他路径借机改变默认精度。
- STFT 测 DC/Nyquist/负频率、不同 hop、边界；CWT 测多个小波、尺度和 halo 接缝；寿命测基线、负/正信号约定、参数边界、失败率和 R²。
- 数值误差使用每种算法/精度的 rtol 与按信号量级确定的 atol，阈值先写入参考测试并结合真实科学要求确认。不能用统一小数点位数覆盖 1e-4 与 65536 的数据，也不承诺跨后端逐 bit 一致。
- 比较双指数结果时考虑参数交换等价性，同时检查可辨识性；有接近阈值而影响分类的结果须显式诊断或进行规定的高精度复核。

### 10.2 有界资源与任务回归

- 无 GPU、未安装 CuPy、自检超时、不支持 dtype、低显存、其他程序抢占显存、磁盘不足、不可写目录。
- 读取中、上传中、计算中、写入中、提交前取消；失败/取消不增加历史，不破坏输入，GUI 可操作，后续任务可运行。
- 连续至少 10 次任务检查资源是否持续增长；取消后的文件映射、进程、共享块、FFT 计划和 pinned memory 释放。
- 更换焦点、切换画布、删除历史、清缓存、恢复缓存与任务同时操作；有效租约防止文件被回收，晚到结果不串任务。
- 用虚拟 shape/惰性块源测试未来 TB 规模规划及 >2^31 计数，不在开发机自动分配 TB 数组或创建巨大文件；此测试不能称为 TB 吞吐验证。
- 最小闭环：导入/恢复 NPY → STFT/CWT/寿命 → ProcessedData → 历史选择 → 画布/ROI → 导出。首批极大数据保证链路以可分块 NPY 为边界；不因此宣称所有压缩 TIFF/HDF5 导入路径都已流式化。

### 10.3 性能证据与 Auto 门槛

基准分为：小型确定性样例、用户日常 float32 样例、当前极端 10000×400×400 的可选真实样例、未来规模的资源规划测试。只有目标机器存储和内存条件满足时才进行未来完整实测，不作为日常测试。

记录磁盘读写、CPU 整理、H2D、GPU 计算、D2H、结果提交、总耗时、峰值 RAM/pinned/VRAM、输出大小和误差；数据驻 RAM/磁盘分别统计。CUDA 异步计算需事件或同步后计时，首次初始化/JIT 与热运行分开。[CuPy 性能计时说明](https://docs.cupy.dev/en/stable/user_guide/performance.html)

对照对象是优化后的 CPU 分块实现，且科学参数、精度策略和输出内容相同。小/中型测至少 5 次取中位数；大真实样例明确次数与系统缓存状态，不通过清理系统缓存或停止用户程序来制造条件。

Auto 可先采用“预计端到端提升至少 1.3 倍且节约至少 0.5 秒”作为待校准启用门槛，不是收益承诺。性能档案按设备、运行库、算法版本、dtype、典型形状和驻留状态区分；无档案保守选 CPU，用户可手动指定 GPU。快速校准使用有限合成数据、可取消，不在启动时偷偷跑用户全量数据。

## 11. 分阶段交付与完成定义

| 阶段 | 工作与产物 | 验收门槛 |
| --- | --- | --- |
| A：冻结计算契约 | 锁定默认精度；CPU 参考样例；修复本轮相关的明确调用/输出缺陷；确认 CWT 多尺度和 STFT 复数约定 | 默认有效路径兼容；单/双指数与 R² 有明确正确性测试；没有悬空的科学定义 |
| B：统一设置与有界 CPU | ComputeRequest、精度表、资源预算、硬件后台探测、设置 GUI、分块 NPY sink；接入现有任务系统 | 无 GPU 可完整使用；不整组复制大输入/输出；设置有效持久化；取消与错误闭环通过 |
| C：CUDA STFT 主闭环 | 设备 worker、能力自检、批量 STFT、按任务进度与回退；可用 FFT2 做基础验证 | 目标 NVIDIA 机器上 float32/双精度分别验证；默认精度不变；真实端到端有证据才纳入 Auto |
| D：CWT 与预处理 | 小波匹配、时间/尺度/空间分块、即时归约、CPU/GPU 一致性；关联预处理流式化 | 单尺度兼容、多尺度正确、块接缝通过；低频/显存不足/取消可控，不建立全量系数体 |
