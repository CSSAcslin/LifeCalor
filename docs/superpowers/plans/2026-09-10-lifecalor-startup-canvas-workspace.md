# LifeCalor 启动反馈与画布工作区实施规划

日期：2026-09-10

基线：`1.0.11`，`65dcbd4 docs: publish 1.0.11 guide`

用途：交由 Sol 在同一项目中实施。本文只定义后续工作，尚未实现的项目均保持未勾选。

## 1. 本轮只解决什么

交付两个用户可直接感知的结果：

1. 启动软件后尽早出现加载界面，显示真实初始化阶段；启动失败有可读原因和日志。
2. 图像显示区成为可用的多画布工作区：四画布等分、原生拖动停靠、浮动、聚焦和布局记忆。

沿用 PyQt5 与现有显示数据流。只为上述结果调整启动装配和画布容器；现有计算器、数据缓存、科学计算结果和伪彩导出行为是需要保护的基线。

本规划取代旧规划中尚未执行的泛化架构任务。实现时以当前源码为准，历史更新日志不能当作能力已全部实现的证明。不要再用“整体完成百分比”验收，以本文交付清单和测试证据为准。

## 2. 旧目标的取舍

| 旧目标/当前状态 | 本轮决定 | 原因 |
| --- | --- | --- |
| 缓存、跨启动恢复、计算器、帧渲染主流程已经过多轮修复 | 作为回归基线 | 没有新故障时继续重写的收益低 |
| MainWindow 仍较大，保留星号导入和大量界面装配 | 取消独立瘦身任务 | 行数不影响用户功能，不为减少行数大规模迁移 |
| ExtraDialog 全部分类迁移、删除全部旧任务文件 | 不列入本轮 | 可维护性收益不足以要求再开一轮广泛重构 |
| 全算法插件化、AlgorithmRegistry 全局接入 | 不列入本轮 | 等到真实新算法需要复用时再局部接入 |
| 任意多任务并发、资源锁、排队优先级 | 留作独立需求，不自动续做 | 任务面板已存在，但登记多任务不等于具备安全调度器 |
| 所有算法的全局内存预算与全面 deepcopy 清扫 | 不列入本轮 | 需独立性能证据；不能仅因出现 copy 就删除 |
| 启动反馈与启动失败提示 | 本轮必做 | 用户启动等待缺少明确反馈 |
| 画布四象限、磁吸、聚焦、布局保存 | 本轮必做 | 用户明确提出，改善比较和交互效率 |
| 空画布工具访问、身份错位、关闭渲染等待 | 随画布改造完成 | 直接影响新布局的正确性和响应性 |
| Windows 原生拖动、多屏和 DPI 验证 | 本轮验收 | 离屏测试不能证明操作系统窗口交互正常 |
| 全格式实测、全性能专项、全局 UI 重设计 | 不列入本轮 | 与本次新增交互无直接关系 |

“未列入”不是仍需 Sol 自动完成的待办。除非用户追加需求，完成本文即结束这一轮。

### 对上一轮结论的必要修正

- 当前 `MemoryBudget.ensure()` 主要用于导入预检；不能宣称所有计算都有全局内存配额。
- 当前 `RenderController.stop_worker()` 存在 `wait(5000)`，画布关闭不是完全异步。
- `TaskPanel` 已有进度和取消，错误内容主要通过 Tooltip 展示；不能等同于完整任务诊断中心。
- 普通数据导入中的“覆盖”当前会清除全部画布。布局改造应明确改成覆盖选定画布，并验证其他画布不受影响。
- 原规划的所有阶段标题或旧测试数量，不应替代对具体行为的确认。

## 3. 执行约束

- 只修改启动链路、画布工作区及直接关联的选择、状态保存、错误接入和测试。
- 不改数组存储协议、历史 manifest 格式、STFT/CWT/寿命算法或计算器表达式语义。
- 不重复扫描已解决的 token 和旧永真判断。
- 不安装、升级或迁移 GUI 框架；本机现有虚拟环境为 `H:\Newera\programing\.venv\Scripts\python.exe`。
- 不新建第二套错误总线；使用现有 `diagnostics`。warning 只记日志/状态，启动失败等 error 才请求弹窗。
- 不把布局操作转化为数组加载或数据复制；不按画布位置重新排列处理历史。
- 保留最多四个画布的限制。浮动画布和暂时隐藏的画布也计入四个。
- 任务面板初始化在控制台所在的右侧底部区域，以“控制台 / 任务”标签切换，不再另占主窗口底部 Dock；默认显示控制台。
- 文档阶段不调整版本。本轮实现先按 `1.0.11` 基线开发；用户验收后统一登记下一补丁版本，默认候选 `1.0.12`，不能覆盖用户自行修改的版本。
- 每次只暂存明确路径；保留用户已有暂存项、实验数据、图标和打包文件。禁止 `git add .`。
- 若发现无关问题，记录简短证据即可；只有确实阻塞本轮验收时才作最小修复。

## 5. 阶段 A：启动加载界面

### 用户体验

- 启动界面使用现有 LifeCalor 图标、名称、当前版本、阶段文字和紧凑进度条，适应 DPI。
- 不人为增加停留时间，不使用计时器把进度虚增到 99%。
- 模块加载等无法预测总工作量的阶段显示“正在加载核心模块”及忙碌状态；可计数步骤显示“已完成 N/M 个初始化步骤”。
- 主窗口可见且必要信号/服务就绪后才关闭启动界面。
- 启动失败保留一个简短错误提示，可查看完整日志；失败后不能出现一个半初始化但可操作的主窗口。
- 点击启动图案不应误关启动页。若提供退出操作，只在安全边界结束启动，不能强杀正在构造的 Qt 对象。

### 接入方式

建议新增轻量入口 `core/launcher.py`，启动相关实现集中到 `core/startup/`。优先采用 `QSplashScreen` 或轻量 QWidget；复用现有资源，不引入 WebEngine。

推荐最少模块：

- `core/launcher.py`：唯一正常启动入口，保留 `multiprocessing.freeze_support()`。
- `core/startup/bootstrap.py`：阶段顺序、异常边界、主窗口交接。
- `core/startup/splash.py`：启动窗口本身。
- 只有为避免导入 MainWindow 才能获取版本时，才增加独立轻量版本常量；主窗口和启动页共用同一值。

顺序必须满足：

1. 轻量标准库和 Qt 导入；调用 `freeze_support()`。
2. 设置 DPI，再创建唯一 QApplication 和应用标识。
3. 安装早期文件日志和启动异常保护。
4. 显示启动界面并完成一次绘制。
5. 加载核心模块、读取设置、装配界面、连接控制器和 worker。
6. 主窗口显示，确认必要服务已就绪，结束启动阶段。
7. 更新检查、缓存扫描等非必要工作在主窗口可用后继续走现有后台任务。

### 线程与兼容要求

- QWidget、QPixmap、ErrorBroker 的 GUI 对象及主界面装配均在主线程创建。
- 不能为了动画流畅而把整个 MainWindow 或带 Qt 副作用的模块导入放入任意工作线程。
- 各阶段之间通过事件循环推进；必要时在受控边界刷新启动窗口，避免任意 `processEvents()` 让半初始化主窗口响应用户事件。
- 重型库单次 import 仍可能短暂占用主线程，应记录实际耗时；启动画面必须在它之前可见。不承诺能对 Python 启动或 EXE 自解压前的时间显示 Qt 进度。
- 如主窗口构造耗时明显，仅把其初始化拆成少数有序步骤。该拆分服务于启动反馈，没有文件行数目标。
- 早期文件日志交接到主窗口控制台时，不能丢失启动记录、重复安装 handler 或产生两次异常弹窗。
- `python core/MainWindow.py` 和 PyCharm 原启动方式需要继续可用。兼容跳转必须位于重依赖导入之前，避免旧入口先花大量时间导入再显示启动页。
- 防止 `__main__`/`MainWindow` 双重执行、循环导入，以及 Windows 多进程子进程弹出主窗口。普通 `import MainWindow` 不得自动启动应用。
- 打包入口如需改变，只修改选定且确认适用的配置；不要顺带整理三份用户 spec。若尚未确认发布配置，明确记录打包验证待办。

### 验收

- [ ] 正常启动能看到实际阶段，主窗口只出现一次，只有一个 QApplication。
- [ ] 模拟某阶段失败，只出现一次错误，日志保留完整异常，无半成品窗口和后台线程残留。
- [ ] 原启动方式和新入口都有效；多进程计算不重复创建启动窗口。
- [ ] 100%/150% 缩放下名称、状态和进度条清晰，没有文字裁切。
- [ ] 记录同机修改前后启动时间及启动页出现时间；若新增明显耗时，解释并消除自身引入的等待。

## 6. 阶段 B：画布身份、焦点和关闭流程

布局之前先补这些行为。否则自由拖动会暴露“列表序号等于窗口位置”的旧假设。

### 身份与选择

- 布局必须操作已有画布对象；拖动窗口不改变 `display_canvas` 数据顺序，不重新编号数据或更换源对象。
- 新增独立稳定的 `layout_key/objectName` 供布局保存使用。推荐从四个工作区槽位中分配空闲 key，关闭后才可复用。
- 保留原业务整数 canvas ID 的兼容方式；不要把整个应用迁移到 UUID。整数重新编号如仍必要，集中同步标题、`data.canvas_num`、焦点和选择框，不能仅改 `canvas.id`。
- `layout_key` 与源数据名称、时间戳、当前屏幕位置无关。
- 普通鼠标点击画布内容或标题即可设为当前画布，并显示克制的焦点边框；不依赖必须先画 ROI 才更新焦点。
- 工具右键配置、导出、ROI、画布详情始终指向正确对象；布局位置不参与数据索引。
- 删除中间画布后再添加，标题、焦点、ROI 选取和导出均不能串位。
- 先修复无画布时 Cursor 的空列表访问，覆盖全删后焦点失效的边界。

### 关闭与覆盖

- “隐藏”“临时聚焦隐藏”“浮动/停靠”“删除”必须是不同动作。
- 用户点击画布标题栏关闭按钮或工具栏删除按钮都执行删除并释放四画布槽位；聚焦模式内部的临时隐藏不等同于关闭。
- 删除画布会停止播放、阻止新渲染提交、关闭详情窗口、断开数据交互信号，再请求 worker 结束。
- GUI 回调内不得调用长时间 `QThread.wait()`。慢渲染尚未结束时，待退役线程、worker 及其数据引用必须被保留到 `finished`，不能随 Dock 删除。
- 丢弃关闭后的返回帧；清理必须幂等，不能重复删除或向已销毁控件发送结果。
- 同一轮覆盖最多保留必要的退役渲染工作，不允许用户连续覆盖无限积累线程。
- 导入新数据后“覆盖”改为明确覆盖一个选定画布，默认当前画布；其他画布数据与布局保留。
- 无画布时直接新增；已满四个时明确提供覆盖对象或取消，不再先创建数据包装后静默丢弃。
- 覆盖同一槽位保留位置和 `layout_key`，但新数据的 ROI、帧号、时空参数按新数据初始化，不能沿用旧 ROI。
- 仅移动/缩放现有画布则保留全部图像交互状态。

### 验收

- [ ] 0 个画布工具点击、删除中间项、全删重建均安全。
- [ ] 移动后 ROI、同步播放、伪彩、详情、导出仍绑定原画布。
- [ ] 慢渲染期间删除/覆盖，GUI 心跳持续，旧线程最终退出，无 QThread 销毁警告。
- [ ] 覆盖指定画布不会清空其他三个，也不会保留旧数据 ROI。

## 7. 阶段 C：等分、磁吸与聚焦

### 默认排列

四象限指“图像显示”区域内部，保留左侧参数区和右侧结果区的现有总体结构。

| 有效画布数 | 默认排列 |
| --- | --- |
| 0 | 简洁空状态，提供现有添加数据入口；不创建虚假数据/渲染 worker |
| 1 | 填满图像工作区 |
| 2 | 左右等分；用户可以切换为上下等分 |
| 3 | 左侧一张占半宽，右侧两张上下等分 |
| 4 | 左上、右上、左下、右下 2×2 等分 |

“四象限”预设在四个画布时可用；不为一到三个画布引入持有假数据的占位画布。无历史布局时采用上表；恢复成功的用户布局优先。

等分按可用内容区计算，扣除标题栏、分割条和工具栏。正常尺寸下各半区差异允许少量像素舍入；不能仅以调用了 `splitDockWidget` 作为等分已成功的证据。

### 原生 Qt 布局

新增 `core/display/layout_manager.py` 管理画布布局。尽量沿用 `ImageDisplayWindow(QMainWindow)` 与 `SubImageDisplayWidget(QDockWidget)`，无需先把 2400 行显示类整体拆开。

- 启用嵌套 Dock，保留原生移动与浮动。
- 显式分割同一 Dock 工作区形成两列，然后分别分割两列，可靠生成 2×2。
- 使用 `resizeDocks()` 在布局完成后设定等分尺寸，必要时以单次延迟执行等分。
- 为内部 QMainWindow 设置合法轻量 central widget，避免额外空白挤占画布；其尺寸行为必须实测。
- 禁止通过反复销毁/重建画布来应用预设。
- 设置标题/工具栏的稳定 objectName，使 Qt 布局保存可正确关联。
- 不启用会强制把四幅图叠成标签的 ForceTabbedDocks。本轮以同时比较为主，不增加标签组管理需求。
- 布局切换有事务标志，避免过程中信号把临时布局误保存。
- 用户手动调整后保留比例，不能在每个 resizeEvent 重设为默认布局。
- 浮动画布收回到工作区时保留原对象。应用全体等分预设表示把现有画布统一收回并排列，命令 Tooltip 写清影响。

Qt 本身提供 Dock 分割和状态保存接口，技术依据见 [Qt 5 QMainWindow 文档](https://doc.qt.io/archives/qt-5.15/qmainwindow.html)。本文的布局规则是 LifeCalor 的产品选择，需要针对现有窗口实测。

### 磁吸的明确定义

本轮磁吸为：拖动画布标题栏到图像工作区或另一画布边缘，出现 Qt 原生停靠提示，释放后重新排列；允许拖出成为浮动窗口。

本轮不做任意浮动窗口之间的边缘吸附、不做操作系统桌面贴边算法、不替换全应用 Dock 引擎。若原生拖动不能满足上述已限定行为，先提交复现证据和局部原因，不自动引入新 GUI 依赖。

### 命令与聚焦

画布工具栏增加紧凑布局图标菜单：

- 自动排列
- 左右等分/上下等分（两个画布时）
- 四象限（四个画布时）
- 聚焦当前画布/恢复全部画布
- 重置布局

复用资源中的图标或 Qt 标准图标，提供中文 Tooltip。窗口标题能看到简短编号和数据名，完整名称通过 Tooltip 查看。

聚焦只临时显示当前画布，其余画布及其源数据仍保留。恢复必须回到聚焦前的分割、浮动和可见状态，不能回到默认排列。不要把聚焦时的隐藏状态写入永久布局。

聚焦期间如需要删除/覆盖/新增画布，先有序退出聚焦再执行该动作，避免构造复杂的隐藏画布变更规则。绘制区双击不用于切换聚焦，防止与现有图像操作冲突。

### 拖动与渲染边界

- 拖动、浮动和更改大小不得触发原数组完整读取、统计或伪彩重新生成。
- 视口大小变化时，默认适配视图可以重新 fit；用户已手动缩放/平移的视图应保持中心与缩放意图。
- 避免高频 resize 形成渲染请求风暴；优先复用已生成图像，仅在必要时合并刷新。
- 布局前后保持当前帧、ROI、伪彩边界、同步选项和播放状态。若底层确需短暂暂停，要恢复之前状态。
- “请移动鼠标”旧覆盖文字随本轮清理，首帧仍由现有自动渲染驱动。
- 不改变像素方向、THW 约定、Hover 实际值和逐帧导出。

### 验收

- [ ] 1/2/3/4 张画布排列符合表格；4 张在不同窗口尺寸下均形成可用的 2×2。
- [ ] 原生拖动可停靠、浮动并重新停靠；不会意外进入外层参数区/结果区的布局。
- [ ] 拖动、等分、聚焦恢复后，源数组/画布实例未替换，当前帧、ROI 和伪彩不丢失。
- [ ] 画布较小时播放控件和时间轴不相互覆盖；窗口过小时遵循合理最小尺寸。
- [ ] 四画布播放时重复调整布局，不出现整段数据复制或不断累积的渲染请求。

## 8. 阶段 D：布局记忆、回归与交付

### 保存什么

复用 QSettings，新增带 schema 版本的画布布局命名空间。保存布局模式、有效槽位集合、Dock state、浮动位置等小型 UI 数据，禁止把数组或历史恢复信息写入布局配置。

- 同一会话改变布局后延迟保存，避免每个像素拖动都写配置。
- 普通用户隐藏与聚焦临时隐藏分开处理，保存时不能把所有画布记成不可见。
- 布局按有效槽位集合/数量匹配；跨启动槽位可复用，但不承诺恢复相同数据。
- 启动后没有画布时，延迟布局恢复到相应画布存在；不能为恢复布局自动加载历史缓存。
- 新建到相同槽位组合时恢复对应布局一次，不能每次渲染都恢复。
- 当前数据变化导致布局签名不匹配时采用默认排列，用户手动布局不得被无关信号反复覆盖。
- 浮动位置按当前屏幕 availableGeometry 校正。拔掉副屏后所有画布必须仍可找回。
- 状态损坏、版本不匹配、restoreState 失败：记录一次 warning 并回退到默认排列。
- “重置布局”清除本轮布局偏好并收回画布，不清理数据、ROI 或缓存。
- 退出保存时排除聚焦和关闭流程的临时状态。

### 必要自动测试

新增测试按行为组织，可集中在 `tests/test_startup_flow.py`、`tests/test_canvas_workspace.py`；不要求为每个小文件创建对应测试。

| 场景 | 必须验证的行为 |
| --- | --- |
| 启动成功/失败 | 顺序、唯一 QApplication、失败一次上报、服务清理 |
| 旧入口/多进程子进程 | 没有双启动、循环导入、子进程创建 GUI |
| 0/1/2/3/4 个 Dock | 实际 geometry、数目、空状态和默认排列 |
| 移动/聚焦/预设切换 | 同一实例、相同数据源、帧/ROI/伪彩状态保留 |
| 慢 worker 关闭 | GUI 心跳继续、完成后释放、晚到结果被丢弃 |
| 删除中间画布再新增 | 身份不混用，选择/导出/同步绑定正确 |
| 覆盖选定画布 | 只改变目标，清理目标旧 ROI |
| 保存恢复/损坏配置/副屏缺失 | 恢复或明确回退，没有屏幕外窗口和假数据加载 |

已有只搜索源代码字符串的测试可随接入点调整，但不能把“方法存在”当作交互正确。先用小型非方形非对称数组验证方向和 ROI，再用超过落盘阈值的合成/真实数据检查布局操作无整数组复制。

受控尺寸下，四象限 geometry 可按扣除标题与分割条后的比例断言，允许约 2% 的平台差异；不能用完全一致的屏幕像素硬编码跨 DPI 结果。
